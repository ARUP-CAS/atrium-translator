## 🎯 Goal

Two asks in one issue, with different shapes:

1. **Operational** — run the shipped tool (LINDAT/CUBBITT default backend, wrapped in the XML editing pipeline) against real ARÚP/ARÚB documents or AMCR metadata objects, in a real environment, and collect feedback. Gated on the repo being "ready by Opus opinion" and compliant with [`ufal/atrium-project#53`](https://github.com/ufal/atrium-project/issues/53).
2. **Design** — decide whether the tool should **replace** `SRC`-language fields with `TRG` (English), or **extend** the input by **appending** `TRG` fields alongside the `SRC` ones.

They are related but not blocking on each other: the design question can be answered from the code and samples now, and the answer should shape what reviewers are asked to look at during the run.

## 🔬 The big question — what the code does today

**Today the tool replaces. It is two lines.**

| Path              | Line                           | What happens                                                              |
|-------------------|--------------------------------|---------------------------------------------------------------------------|
| AMCR metadata XML | `utils.py:160`                 | `elem.text = translated` — the Czech text node is overwritten             |
| ALTO XML          | `utils.py:513`, `:515`, `:517` | `string_elem.set("CONTENT", …)` — the Czech word attribute is overwritten |

`main.py:285` documents `--alto` as *"Enable ALTO XML **in-place** translation mode."* There is no append mode, no `--output-mode` flag, and **no code path anywhere in the repo writes `xml:lang`, ALTO `@LANG`, or `<ALTERNATIVE>`** — so nothing in the output declares that it is English, or that a machine produced it.

**But the framing in the issue hides a distinction the codebase already makes.** The tool *does* append — just at the wrong granularity to answer the question:

- **At artifact level it appends.** The source file is never modified; a sibling `<name>_en.xml` / `<name>_en.alto.xml` is written next to it, plus a `<name>_log.csv` holding every `(xpath, source, translation)` triple, plus a paradata JSON.
- **At field level it replaces.** Inside that new artifact, the Czech is gone.
- **The Document JSON is already the project's declared accretion surface.** `main.py:298` describes `--document-json` in exactly these words: *"Optional baseline ATRIUM Document JSON to append to (**accretion model**)."* `utils.py:172-173` notes the translated corpus persists there via `derived_from.translated_xml`.

So the real question is not *replace or append* but **at what granularity the English lives** — and the project has already answered it once, for the JSON record. The XML has simply not been brought into line.

## 🧾 Evidence from the shipped samples

### AMCR metadata — `C-N1000019.xml` → `C-N1000019_en.xml`

Three free-text fields are rewritten in place; everything else is untouched:

```xml
<!-- input  --> <amcr:nazev>Davle - kultovní areál 1 - klášter sv. Jana Křtitele na Ostrově</amcr:nazev>
<!-- output --> <amcr:nazev>Davle - ritual site 1 - monastery St. John the Baptist on the Island</amcr:nazev>
```

Measured across all 15 AMCR samples in `data_samples/my_documents/`:

| Observation                                                                          | Count                                                             | Consequence                                          |
|--------------------------------------------------------------------------------------|-------------------------------------------------------------------|------------------------------------------------------|
| `xml:lang="cs"` attributes                                                           | **426**                                                           | AMCR marks language routinely…                       |
| `xml:lang` of any other value                                                        | **0**                                                             | …but only ever Czech in this corpus                  |
| Element types carrying `xml:lang`                                                    | **23**, all controlled-vocabulary (`id="HES-…"` / `id="ruian-…"`) | Language tags live on thesaurus terms                |
| The 3 translated free-text fields (`nazev`, `popis`, `poznamka`) carrying `xml:lang` | **0**                                                             | The rewritten fields carry no language marker at all |

The asymmetry this produces is the practical problem. In the output file, `<amcr:okres xml:lang="cs">Praha-západ</amcr:okres>` still declares Czech (correctly — it was not translated), while two elements away `<amcr:nazev>` now holds English and declares nothing. **A harvester cannot tell the file apart from a Czech original except by reading it.**

### AMCR already answers this question — in AMCR's own vocabulary

`load_vocab.py:124-134` builds the glossary by walking AMCR thesaurus records:

```python
for child in heslo_block:
    if child.tag == f"{{{amcr_ns}}}heslo" and child.get(xml_lang) == "cs":
        cs_text = (child.text or "").strip()
    elif child.tag == f"{{{amcr_ns}}}heslo_en":
        en_text = (child.text or "").strip()
```

**AMCR stores Czech and English as sibling elements under one concept `@id` — `heslo` and `heslo_en`.** That is append, in production, in the source system this tool reads from. The repo consumes append-shaped AMCR data every time it rebuilds the glossary, and emits replace-shaped output. Recommending "append" is therefore not inventing a convention; it is adopting the one the data already uses.

A corollary worth acting on separately: for the 23 controlled-vocabulary element types, the correct operation is **thesaurus lookup by `HES-` id**, not machine translation — deterministic, reviewable, already licensed. `load_vocab.py` harvests exactly those `id → (cs, en)` triples and then **discards the id** when it flattens to the two-column `data_samples/vocabulary.csv` (5087 pairs). The identity is available and thrown away.

### ALTO — `MTX201501307_anon.alto.xml` → `MTX201501307_anon_en.alto.xml`

Structure is preserved exactly; only `CONTENT` changes:

| | Pages | TextBlocks | TextLines | Strings | `CONTENT=""` | multi-word `CONTENT` |
|---|---|---|---|---|---|---|
| input | 79 | 1193 | 2095 | 7229 | **0** | **0** |
| output | 79 | 1193 | 2095 | 7229 | **224** | **304** |

Every input `String` holds exactly one word. In the output, **528 of 7229 (7.3%)** no longer do — 224 were blanked, 304 hold two or more words — and **not one of the 7229 bounding boxes was resized**. Concretely:

```xml
<String CONTENT="Záchranný"   HEIGHT="51" WIDTH="250" VPOS="992" HPOS="843"/>   <!-- input  -->
<String CONTENT="rescue"      HEIGHT="51" WIDTH="250" VPOS="992" HPOS="843"/>   <!-- output -->

<String CONTENT="archaeological research and is therefore protected by the copyright law"
        HEIGHT="33" WIDTH="115" VPOS="2953" HPOS="2069"/>                        <!-- 71 chars in a 115px box -->
```

This is structural, not a bug. `_align_tokens_to_lines` (`utils.py:233-277`) takes **one block-level translation**, splits it on whitespace, and re-buckets the tokens across physical lines by `difflib` similarity against per-line anchor translations; the last `String` on each line absorbs the remainder. **The 1:1 word-to-box correspondence in the output is fabricated.** Semantic casualties are visible in the same file — `Vraní,` (a place name) → `Crow,`, `ČOV` → `OV`.

The conclusion this forces: **"append per `String`" is not a coherent option for ALTO.** There is no word-level correspondence to append to. The only honest shapes are a parallel artifact (what already happens) or block-level translated text stored once.

## 🧭 Recommendation

Not one verdict — the two formats have genuinely different answers.

| Format                                | Recommendation                                                                                                                                        | Why                                                                                                                                                                               |
|---------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **AMCR metadata XML**                 | **Append.** Emit an English sibling element carrying `xml:lang="en"` next to the retained Czech, following AMCR's own `heslo` / `heslo_en` precedent. | The fields are few (10 XPaths in `amcr-fields.txt`), short, and harvested into catalogues where losing the Czech original is not acceptable. The source system already does this. |
| **AMCR controlled-vocabulary fields** | **Look up, don't translate.** Resolve `HES-…` / `ruian-…` ids against the harvested thesaurus.                                                        | Deterministic and authoritative; `load_vocab.py` already harvests the pairs. MT on a thesaurus term is strictly worse than the term.                                              |
| **ALTO**                              | **Keep the parallel `_en.alto.xml` artifact.** Do not attempt per-`String` append. Do label the output's language and record provenance.              | Word-level alignment is fabricated; appending it would multiply a fiction rather than preserve evidence.                                                                          |
| **Both**                              | **Treat the ATRIUM Document JSON as the accretion surface.**                                                                                          | `main.py:298` already calls it that. It is the one place a language-keyed structure costs nothing.                                                                                |

**The Document JSON can carry an appended pair today, with no schema change.** Three facts make this the cheapest place to start:
- `atrium_document.schema.json` sets `additionalProperties: true` on the root and on the `translations` block, and `to_dict()`'s rule 6 preserves unknown or newer blocks — so a per-field bilingual payload can be written into `translations` without touching the frozen 1.0 schema (the constraint is governance under `atrium-project#54`, not the data model).
- **The ecosystem already has a suffix-append precedent in this exact record**: `enrichment.items[].extracted_keywords_cs` / `_en`, written by llm-enrich.
- The schema *already declares* `entities[].translation_en`, and `atrium_document.py`'s ownership table assigns it to **this repo** — yet no code path writes it. `utils.py:175-177` calls it "UNIMPLEMENTED, not merely deferred". An append-shaped field the translator owns is sitting unused.

The single sentence for the issue: **append for metadata, parallel artifact for ALTO, and mark the language either way** — because the current output is unlabelled English that a consumer cannot distinguish from the Czech original, and that is the defect worth fixing first regardless of which mode wins.

## 🚧 The one blocking unknown

Whether the AMCR XSD permits **repeated** `nazev` / `popis` / `poznamka` elements — i.e. their `maxOccurs`. If they are `maxOccurs="1"`, an appended sibling makes the document schema-invalid and unfit for OAI-PMH re-publication, and the English has to go somewhere else (an attribute, a wrapper, or JSON only).

**This was not verifiable here**: `https://api.aiscr.cz/schema/amcr/2.2/amcr.xsd` is unreachable from this environment (curl exit 56) and no local copy exists in either repo. It must be checked before any append design is committed to — it is a ten-minute check for anyone with network access to `api.aiscr.cz`, and it decides the whole shape.

Note also that `--xsd` is **opt-in and off by default** (`main.py:287`), **warn-only** rather than fatal, and **never applied to ALTO at all** — `process_alto_xml` takes no `xsd_schema` parameter, so only the metadata path is ever validated. Because replace never alters structure, the validation gate is trivially satisfied today; it only becomes load-bearing the moment append exists. The README's claim (`README.md:84`) that XSD validation *"guarantee[s] structural integrity after translation"* is true but currently vacuous.

## ⚠️ What a real production run will expose

Findings from reading the pipeline that the in-prod experiment should be instrumented to catch:

- **🛑 `/translate` does not translate metadata at all.** `service/api.py:326` hard-codes `xpaths_list=[]` into the `process_single_file` call, and the endpoint exposes no way to supply XPaths — only the CLI reads them, from the `fields` file (`main.py:552-555`). With an empty list, `process_metadata_xml`'s `for xpath in xpaths:` loop (`utils.py:143`) never runs, so **`POST /translate?is_alto=false` returns HTTP 200 with the document re-serialised but untranslated.** The CLI path is unaffected. If the experiment targets AMCR metadata objects *through the service*, this is a showstopper and must be fixed before handover — it is also exactly the class of defect the stubbed integration lane cannot see, since a stub returning nothing and a pipeline asking for nothing look identical.
- **`is_alto` is a query parameter, not a form field.** `service/api.py:209-211` declares `source_lang`, `target_lang` and `is_alto` as bare scalars on a `POST`, so FastAPI binds them from the query string. Sending `is_alto=false` in the multipart body — which the repo's own tests do — is silently ignored and the request runs in ALTO mode. Worth stating explicitly in the handover instructions.
- **Throughput is bimodal, and nothing measures it.** `_translate_batch` (`utils.py:433-460`) joins a page's blocks — and separately its lines — with `\n` into a single LINDAT call. If the returned line count does not match, it falls back to **one call per item**, via an unlogged `if` miss and a bare `except Exception: pass`. For the 79-page sample that is roughly **158 calls** in the good case and up to **~3288** in the bad one, with no counter distinguishing them. This is the most likely cause of "why did that document take twenty minutes", and the cheapest thing to fix before the run.
- **No idempotency guard.** Re-running the tool on an `_en` output re-translates English into English. With an explicit `--source_lang` there is not even language detection to notice. In a production loop with retries, this is a live hazard.
- **Licence inheritance.** `config.txt` defaults to `source_lang = auto`, which loads FastText and pulls **CC BY-NC 4.0** into the paradata licence set; the default LINDAT backend contributes **CC BY-NC-SA 4.0** (`para_config.txt [components]`). Real ARÚP/ARÚB output inherits the most restrictive component. Passing `--source_lang cs` explicitly avoids the FastText component (`para_config.txt` marks it `conditional`), and is worth doing on a Czech-only corpus anyway.
- **Synchronous request shape.** The hub's own deployment reference (`docs/k8s_deployment.md`, "Known limits") already flags that translator processes a request inside the HTTP cycle and that a request outliving the grace period is cut. The runbook calls `/translate` *"the slowest request shape in the fleet"*. Combined with the bimodal call count above, `GRACEFUL_SHUTDOWN_S=20` is the number most likely to need raising.
- **There is a live-LINDAT lane, and it has never been run.** `.github/workflows/integration.yml` declares two deliberately asymmetric jobs: `stub-backend`, which runs on every push against `tests/integration/stub_lindat.py`, and **`live-backend`, which runs the same tests against the real LINDAT hosts and is manual-only** (`workflow_dispatch` + `inputs.live`). The workflow's own header explains the asymmetry — *"if CUBBITT changes its response shape, the stub lane stays green"* — and prescribes running it *"before a release"*. **The GitHub API reports 0 `workflow_dispatch` runs of this workflow.** So the automatic signal is entirely stubbed, the real-contract check exists but has never fired, and the release it was meant to precede has already been cut. Dispatching it is the cheapest possible pre-flight for #46 and arguably a precondition.
