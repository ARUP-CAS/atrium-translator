# Strategy — Issue #46: Run the Translator In Production and Settle Replace-vs-Append

## Context

The repo is at **`v1.0.0-beta`** and the twelve-factor gate named in the issue is substantially met. What remains is not more hardening: it is the one thing no test in this repository can do, which is send a real ARÚP/ARÚB document through the real LINDAT service and have a domain expert read the result.

`tests/integration/test_translate_live.py` runs the real handler, the real pipeline and the real ALTO reconstruction — against `tests/integration/stub_lindat.py`. It closed the wiring gap that shipped a `backend`-less HTTP 500. It says nothing about translation quality, real-world throughput, or whether the output shape is usable by the institutes. **That is the gap #46 exists to close.**

Two blockers stand between here and the handover, and neither appears on the issue tracker:

- **The beta's container image tags were never published.** The hub's release gate failed on fixable CRITICAL CVEs in the `python:3.11-slim` base for both matrix targets, and the promotion step is `if: success()` — so `v1.0.0-beta` exists by digest only; `:1.0.0-beta` and `:latest` were never applied. Nothing can be pulled by name.
- **`test` is 5 commits ahead of the tag**, and those commits contain the fix for exactly that failure, plus a 210-line `.env.example` rework and three new contract test files. The artifact called "BETA" predates the hardening the beta was cut to deliver.

Separately, the design question can be answered now. The digest argues it in full; the short form is **append for AMCR metadata, parallel artifact for ALTO, and mark the language either way**. Per the scope agreed for this plan, no append implementation is scheduled here — the recommendation is recorded, the experiment runs in today's replace-only mode, and the decision is taken on returned feedback.

## Execution Plan

### Phase A — Make something handover-able

**A1. Re-cut the release.** Tag from current `test` (`9068759` or later) rather than re-releasing `30aab7e`. Two reasons: the CVE fix that unblocks the publish gate is only on `test`, and the `.env.example` / `Dockerfile` / contract-test work that the beta was announced for is only on `test`. Then **verify the tags actually landed** — a green workflow run is not the evidence; the presence of `:1.0.0-beta.N` and `:latest` in the registry is. The previous run went green on `release.yml` (the bundle) while the image promotion never fired, which is precisely how this was missed.

**A2. Reconsider the `prerelease` flag.** `v1.0.0-beta` is published with GitHub's `prerelease: false`, so a beta currently presents as the repo's latest stable release. If ARÚP/ARÚB or any downstream consumer resolves "latest", this is what they get.

**A2b. Fix `/translate` for metadata objects — or scope the experiment to ALTO.** `service/api.py:326` hard-codes `xpaths_list=[]` into the `process_single_file` call and the endpoint offers no way to supply XPaths; only the CLI reads them, from the `fields` file (`main.py:552-555`). The consequence is that **`POST /translate?is_alto=false` returns HTTP 200 with the document re-serialised and untranslated.** The CLI path works correctly. So either the endpoint learns to load `amcr-fields.txt` (or accept an XPath list), or the metadata half of the experiment runs through the batch CLI and the handover says so explicitly. Note too that `is_alto`, `source_lang` and `target_lang` are **query** parameters (`service/api.py:209-211`), so `is_alto=false` sent in the multipart body is silently ignored and the request runs in ALTO mode — a trap the repo's own tests currently fall into, and one worth spelling out in the handover instructions.

**A2c. Dispatch the `live-backend` lane — it has never been run.** `.github/workflows/integration.yml` already carries a job that runs the integration tests against the **real** LINDAT endpoints, gated behind `workflow_dispatch` + `inputs.live`. Its own header says to run it *"before a release"*. The GitHub API reports **zero** `workflow_dispatch` runs of that workflow, and `v1.0.0-beta` was cut without it. This is a one-click check that the real CUBBITT contract still matches what the stub asserts, and it costs nothing — run it before anything is handed to a partner.

**A3. Instrument the batch fallback.** `_translate_batch` (`utils.py:433-460`) silently degrades from one call per page to one call per block/line when the returned line count does not match the input — via an unlogged `if` miss and a bare `except Exception: pass`. Add a counter and a single log line per document. Without it, throughput feedback from the run is uninterpretable: the difference between ~158 and ~3288 LINDAT calls for the same 79-page document is invisible in the output. This is the highest value-per-line change available before the run.

**A4. Settle the AMCR XSD question.** Fetch `https://api.aiscr.cz/schema/amcr/2.2/amcr.xsd` and read `maxOccurs` for `nazev`, `popis`, `poznamka`. If they are `maxOccurs="1"`, appended siblings make the document schema-invalid and the append design has to move (attribute, wrapper element, or Document JSON only). This could not be checked from the development environment — the host is unreachable there. It is a short task for anyone with network access and it decides the whole shape.

**A5. Decide the run's licence posture.** Pass `--source_lang cs` explicitly rather than relying on `config.txt`'s `source_lang = auto`. Auto-detect loads FastText, which `para_config.txt` marks `conditional` and **CC BY-NC 4.0** — inherited by every output. On a Czech-only corpus the detector buys nothing. The LINDAT backend still contributes CC BY-NC-SA 4.0; the institutes should be told what licence their outputs carry before the run, not after.

### Phase B — Hand over

**B1. Resolve the recipient.** See Open questions — this is K4TEL's call and it changes the corpus.

**B2. Package what the institutes need.** The hub already has all three pieces:
- `atrium-project/docs/k8s_deployment.md` — the deployment reference
- `atrium-project/docs/templates/k8s/atrium-service.deployment.yaml` — the manifest
- `atrium-project/docs/k8s_acceptance_runbook.md` — the procedure, with translator's smoke request already specified: `curl -s -X POST localhost:8000/translate -F "file=@<large.alto.xml>"`, described there as *"the slowest request shape in the fleet"*

**B3. Respect the governance boundary.** Per `atrium-project/agent_dev_logs/plans/40.plan.md:10-11`, **GitHub Actions must not be wired to any ARÚP/ARÚB environment**; the boundary is a Docker image built and run entirely inside their own environment. The acceptance runbook says the same in its own words — no cluster is in scope hub-side. So this cannot be driven from CI or from a development session. It is a genuine handover, and the plan should not pretend otherwise.

**B4. State the known limits up front.** `docs/k8s_deployment.md`'s "Known limits" section already warns that translator handles requests synchronously inside the HTTP cycle and that a request outliving the grace period is cut. Given A3's call-count spread, flag `GRACEFUL_SHUTDOWN_S=20` (and `terminationGracePeriodSeconds`) as the first dial to raise for large ALTO inputs, and `MAX_UPLOAD_MB=50` as the second.

### Phase C — Run it

Follow the hub runbook's shared procedure: apply the manifest, wait for the startup probe, confirm the probe contract from inside the cluster, then send real traffic and trigger a rolling restart mid-flight to confirm nothing in flight fails. Fill in **translator's row** in the runbook's *Results log* table (deploys clean / probes behave / rolling restart drops nothing / non-default `PORT` / env contract honoured).

Worth saying explicitly in the handover note: **this same run closes hub [#55](https://github.com/ufal/atrium-project/issues/55)'s external acceptance criterion for translator** — the one hub #53 records as *"not ours to close"*. One deployment advances three issues.

Run both corpora if the recipient question resolves to "both": AMCR metadata objects exercise `utils.py:160` and the 10 XPaths in `amcr-fields.txt`; ALTO pages exercise the token realignment and the geometry question. They fail in different ways and only the first is cheap to fix.

### Phase D — Collect feedback that answers the question

Generic "how did it go" will not settle the design question. Put these specifically:

1. **Is unlabelled English acceptable?** Show a translated AMCR record where `<amcr:okres xml:lang="cs">` sits two elements from an `<amcr:nazev>` that now holds English and declares nothing. Ask whether a harvester on their side can live with that.
2. **Do you need the Czech in the same file?** This is the replace-vs-append question in the only form that matters. Note that AMCR's own thesaurus already answers it with `heslo` / `heslo_en` siblings — ask whether they expect that pattern to extend to records.
3. **Does the ALTO geometry matter to you?** Show the measured damage: 224 blanked and 304 over-filled `String` boxes out of 7229, none resized. If they render or search on coordinates, replace-mode ALTO is not usable and the parallel-artifact reading is confirmed from their side rather than ours.
4. **Should controlled-vocabulary fields be resolved from the thesaurus?** The 23 `HES-`/`ruian-`-identified element types are currently untouched. Ask whether they want authoritative English labels there, which is a lookup rather than a translation.
5. **Which entry point do you want to use?** Batch CLI over a directory, or the HTTP service per document. This is not cosmetic — see A2b; the two paths do not currently have the same capability for metadata.
6. **Throughput and failure modes** — wall-clock per document, anything that timed out, anything that came back empty.

Record the answers under `agent_dev_logs/` and, per the runbook's own instruction, return the completed Results-log table.

### Phase E — Decide and hand off the implementation

With feedback in hand, take the decision on the issue thread and open a separate implementation issue for whichever shape wins. That follow-up — not this issue — carries the `--output-mode` design, the schema work, and the downstream contract changes. #46 closes when the run has happened, the feedback is recorded, and the decision is written down.
